# LivingMansion

- 문서 유형: 게임
- 문서 버전: 1.0
- 프로젝트 버전: 0.1.2
- 근거 신뢰도: 낮음

## 1. 문서 메타데이터와 근거 범례

본 GDD는 파일 시스템에 존재가 확인된 파일 목록(경로)만을 근거(Fact)로 사용하며, 본문 내용은 권한 거부로 열람하지 못해 대부분 추론(Proposal)으로 표기함. 표기 규칙: [사실] = 파일/경로 존재 확인, [제안] = 파일명·구조로부터의 추정 또는 설계 제안. project_version은 `LivingMansion_v0.1.2_portable.exe` 파일명에서 확인된 값([사실]).

## 2. 문제 정의

[제안] 플레이어가 제한된 자원과 공간 안에서 유닛(영웅)을 배치해 침입하는 적의 웨이브를 막아야 하는데, 배치 판단이 늦거나 잘못되면 방어선이 무너지는 반복적 좌절이 발생한다. 이는 `PlacementScreen.scn`, `Enemy.scn`, `ResultScreen.scn` 존재([사실])로부터 배치→전투→결과 확인 구조가 있다고 추정한 것이며, 실제 문제 서술은 기획서 본문 미확인 상태.

## 3. 한 줄 피치와 제품 포지셔닝

[제안] '한정된 시간 안에 영웅을 배치해 저택을 지키는 캐주얼 디펜스 게임'. 포지셔닝은 라이트 전략/디펜스 장르로 추정되며, 정확한 차별화 포인트는 기획서 본문(`LivingMansion_기획서.md`) 열람 후 확정 필요.

## 4. 주 페르소나

[제안] 이름: 김도윤(가명), 32세, 스타트업 프론트엔드 개발자. 퇴근 후 15~20분 짧은 세션으로 모바일/PC 캐주얼 전략 게임을 즐기며, 복잡한 튜토리얼보다 즉각적인 배치-결과 피드백을 선호. `persona_playtest_feedback.md` 파일이 존재([사실])하므로 실제 플레이테스트 대상 페르소나가 별도 정의돼 있을 가능성이 높으나 본문 미확인으로 위 페르소나는 임시 제안임.

## 5. 디자인 기둥과 핵심 재미

[제안] (1) 빠른 배치 판단의 긴장감, (2) 영웅 조합(Knight/Mage/Hero)에 따른 전략적 선택, (3) 메타 성장을 통한 반복 플레이 동기부여. `test_meta_upgrades.gd` 존재([사실])가 메타 성장 시스템 존재를 뒷받침.

## 6. 핵심 루프

유저가 선택을 하면 결과가 되고, 그 결과 때문에 다시 선택을 한다.

[제안] 정확히 다음 순환 문장으로 표현: '플레이어는 저택 배치 화면에서 영웅을 배치하고, 적의 침입을 방어한 뒤, 결과 화면에서 보상을 확인하고 성장한 영웅으로 다시 배치 화면으로 돌아간다.' 이는 `PlacementScreen.scn → Enemy.scn → ResultScreen.scn → (재)PlacementScreen.scn` 씬 이름 순서([사실])에서 유추한 순환 구조([제안]).

## 7. 최초 30초 플레이 흐름

[제안] 게임 시작 → 배치 화면 진입 → 기본 영웅(Hero) 1기 배치 → 첫 적 웨이브 등장(Enemy) → 방어 성공/실패 즉시 피드백. 실제 튜토리얼 순서나 텍스트는 기획서 미확인으로 추정치임.

## 8. 게임 규칙과 승패 조건

[제안] 저택 체력 또는 방어선이 0이 되면 패배, 웨이브를 모두 방어하면 승리로 추정. 함정 요소로 `spike_fence.res`, 공성 요소로 `catapult.res`가 존재([사실])하나 정확한 수치 규칙(피해량, 웨이브 수 등)은 미확인이라 기재하지 않음.

## 9. 콘텐츠, 진행, 성장, 경제 구조

[제안] 영웅 종류(Knight, Mage, Hero)와 레벨 리소스(`hero_level.res`)가 존재([사실])하여 영웅별 레벨링 시스템이 있는 것으로 추정. 재화/상점 등 경제 구조 관련 파일은 확인되지 않아 기재하지 않음.

## 10. MVP 가설과 검증 방법

[제안] 가설1: '배치→방어→결과 확인'의 1회 순환만으로도 재도전 의사가 발생한다. 가설2: 영웅 3종(Knight/Mage/Hero) 조합만으로 최소 3종 이상의 유효 전략이 존재한다. 검증 방법은 `persona_playtest_feedback.md`, `first_room_prototype_test_rubric.md` 문서를 통한 플레이테스트로 추정되나 본문 미확인으로 실제 검증 결과는 기재하지 않음.

## 11. 레퍼런스별 핵심 행동 단계 수와 적용 교훈

[제안] 레퍼런스 자료(`LivingMansion_레퍼런스_플레이예시_구버전.png`, `LivingMansion_01_플레이예시.png`)가 존재([사실])하나 이미지 분석 없이는 단계 수를 특정할 수 없어 구체적 단계 수는 기재하지 않음. 문서 본문 확인 후 갱신 필요.

[제안] 웨이브 디펜스 벤치마크의 핵심 행동은 방어 유닛 배치 → 웨이브 관전·개입 → 보상으로 재배치의 3단계다. 적용 교훈은 전투 전에 공격 범위와 예상 진입 경로를 미리 보여 주는 것이다.

## 12. 수치 KPI와 측정 방법

[제안] 검증 목표(안): 1회차 세션에서 재도전율(다음 웨이브 재시작 비율) 50% 이상. 측정 방법(안): `ResultScreen.scn` 노출 후 재시작 버튼 클릭 이벤트 로깅. 실제 KPI 수치는 기획서/개선 지시서 본문에 정의되어 있을 가능성이 높으나 미확인 상태.

## 13. UI, HUD, 컨트롤

[제안] 화면 상태 5종(파일명 기반 추정): 배치 화면(`PlacementScreen.scn`), 전투 진행 화면(`Enemy.scn` 기반 실시간 화면), 결과 화면(`ResultScreen.scn`), 커서 기반 조작 안내(`RunAtCursor.scn`), 텍스트 출력/알림(`OutputText.scn`). 각 화면의 정확한 위젯 배치는 씬 파일 내부 미확인.

## 14. 로딩·빈 상태·에러·100개 이상 데이터·3배 긴 텍스트 대응

[제안] 관련 대응 로직을 확인할 파일이 근거 목록에서 식별되지 않음. 영웅/적 개체 수가 100개 이상으로 늘어나는 경우나 긴 텍스트 대응에 대한 근거 없음 — 기획서 본문 확인 필요.

## 15. 접근성

근거 목록에서 접근성(색맹 모드, 스크린리더, 키 리매핑 등) 관련 파일이나 설정이 확인되지 않음. 접근성 대응 여부는 현재 근거로 판단 불가.

## 16. 시각·청각·햅틱 피드백
